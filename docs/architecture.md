# Webdrop 架构草案

本文件保留总体设计方向。当前后端已实现会话、房间、PoW、内容、上传/下载、分享和 SSE；准确运行语义以 packages/contracts/protocol.md 为准，前端业务 UI 仍待实现。

已确认的产品目标见 [GOAL.md](../GOAL.md)，PoW 与页面实现约束见 [开发规范](development.md)。

## 产品范围

在不同设备的浏览器之间分享文字、小文件、图片和视频。借鉴 AirDrop 的低门槛体验，第一阶段以 DropRoom 为共享会话，四位数字房间号同时用作配对码，后续支持扩位；二维码作为未来便捷入口。暂不承诺原生 AirDrop 发现、后台常驻或无需点击的剪贴板同步。

新建 Channel / DropRoom 默认允许持有效房间号者加入，创建者具有管理权。内部房间 ID、可变长度的对外房间号和成员凭证分离，不能仅凭房间号执行管理操作。创建和加入流程预留原生 Swift PoW 防护，尝试次数上升时提高挑战难度，结合限流、冷却与一次性证明；不把 PoW 作为身份认证。

首页规划为大图标与 `WebDrop` 字样，下方为四位数字输入框，右侧依次为随机和加号按钮；不添加冗余介绍。首页与 PoW 组件统一支持亮暗主题。页面与浏览器组件待实现，Swift PoW 防护已实现。

浏览器使用 Clipboard API 需要安全上下文，读取与写入还受浏览器权限和用户操作限制。首版以用户主动粘贴 / 点击复制为基础，保留普通文本输入和手动复制兜底。[Clipboard API 说明](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API)

## 运行边界

前端 SPA 负责交互、浏览器能力调用和展示。Swift API 负责配对、授权、资源元数据、传输会话和临时链接。

开发环境浏览器访问 Vite，同源代理 API；生产环境采用同源反向代理，前后端独立构建和部署。后端不承担前端静态资源构建。

首版拟使用后端中转，便于资源暂存、复制直链和离线领取；后续可增加 WebRTC 直传，但需要单独的信令及 NAT 穿透设计。实时通知已采用 SSE，持久化采用单进程原子 JSON 快照与私有文件；P2P 尚未接入。

| 模块 | 前端目录 / 后端目录 | 负责内容 |
| --- | --- | --- |
| Devices | `features/devices` / `Features/Devices` | 设备身份、配对会话、在线状态、接收确认 |
| DropRoom（待新增） | 模块位置实现时确定 | Channel / 房间生命周期、房间号、成员、创建者管理权限 |
| AbuseProtection（待新增） | 模块位置实现时确定 | Swift PoW 挑战、动态难度、防重放与来源限流；前端自绘验证组件 |
| Clipboard | `features/clipboard` / `Features/Clipboard` | 文本条目、设备间发送、主动复制 |
| Transfers | `features/transfers` / `Features/Transfers` | 文件上传会话、元数据、状态、传输进度 |
| Links | `features/links` / `Features/Links` | 分享授权、易记短码、直链解析、过期与撤销 |

将来按需增加的模型：Device、DropRoom、RoomMember、PoWChallenge、ClipboardItem、Transfer、Asset、ShareLink。内部资源 ID、房间号（兼配对码）、成员凭证和公开分享短码各自独立。

图片、视频都是 Asset 的媒体类型，存储和分享流程复用文件模块；预览和视频播放是媒体能力，不再各建一套上传服务。

## 传输和存储方向

建议先实现“创建上传会话 → 流式写入临时资源 → 校验长度/类型/摘要 → 标记就绪 → 通知接收设备”。中断或未完成资源不能产生有效下载链接。

元数据与文件字节分离：首版已使用本地私有目录与原子 JSON 元数据快照，未来可替换为事务数据库与对象存储适配器。当前未引入 SQLite。临时存储不要放在前端 public 目录。

实现上传前明确单文件上限、总配额和失败回收策略；前端校验只改善交互，后端必须再次校验。服务端按资源 ID 定位文件，不能拼接用户文件名到磁盘路径。

## 易记短链和临时直链

URL 分工（API 和原始直链接口已实现，前端分享页待接入）：

| 路径 | 处理方 | 作用 |
| --- | --- | --- |
| `/s/mint-lake-7k2m` | React 页面 + API 解析 | 人可读的分享页面，展示类型、大小、到期时间和下载入口 |
| `/d/mint-lake-7k2m` | Swift / 受控文件流 | 原始文件内容；图片可显示，视频可播放，普通文件可下载 |
| `/api/v1/links/...` | Swift JSON API | 创建、查询和撤销分享链接 |

短码建议用小写单词组合 + 无歧义随机后缀；使用安全随机数，数据库唯一索引处理碰撞。示例仅表示格式，不代表已评估最终字典和随机空间。公开域名应尽量短，内部 UUID 不直接展示给用户。自定义短码后续再评估。

每个 ShareLink 引用 Asset，记录 `expiresAt` 和撤销状态。建议首版默认 24 小时过期，可选更短有效期；该值已确认为首版默认值。手动或自动关闭房间时同时撤销关联链接。创建链接是主动分享动作，配对设备间传输不自动公开资源。

易记短码本身不等于身份认证。选择“持有链接可访问”模式时，拿到链接的人都能访问；私密模式需额外访问凭证。上线前确定随机空间、解析限流、配对尝试限制与撤销策略，不能复用分享短码作为设备凭证。

每次解析/下载都校验链接状态；过期或撤销后禁止新请求。文件删除由资源到期与引用关系共同决定，不能撤销一个链接就误删仍被其他有效链接引用的资源。浏览器已经下载的数据无法通过撤销收回。

原始直链后续需要：正确的 Content-Type、按媒体类型设置 Content-Disposition、HEAD、流式响应，以及视频 Range/206。Range 用于媒体播放器随机读取；不能用 JSON/base64 包装视频代替文件流。[HTTP Range 说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests)

到期语义先定义为“到期后不允许新读取”，已经建立的传输是否中止另行确定。公开缓存必须服从有效期与撤销策略，不能让 CDN 长期缓存临时文件。HTML/SVG 等主动内容默认作为附件下载，未来需要内联时使用隔离的资源域名。

## 未来 API 命名空间

- `/api/v1/devices`、`/api/v1/pairings`：设备和配对。
- `/api/v1/rooms`：DropRoom 创建、加入与成员管理的候选入口。
- PoW 挑战签发与验证端点在协议确定后命名；不提前注册可绕过防护的空接口。
- `/api/v1/clipboard`：文本分享。
- `/api/v1/transfers`、`/api/v1/assets`：上传会话、资源元数据与状态。
- `/api/v1/links`：分享管理。
- `/api/v1/events`：实时通知候选入口，传输协议待定。

这些是设计时的模块边界。当前采用 rooms、uploads、assets 等实际路径，具体以 `packages/contracts/openapi.yaml` 和 `protocol.md` 为准。

首版房间与 UI 默认规则已确认，见 [GOAL.md](../GOAL.md)：随机/指定号码创建、聊天式内容流、历史可见性、成员与创建者管理、10 台设备、100 MB 单文件、无人在线 30 分钟关闭和链接默认 24 小时。其余草案不得覆盖这些已确认要求。
